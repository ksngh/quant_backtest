# Daily Report Style Rules

이 문서는 full daily report workflow에서 `report-ko.html`에 들어갈 한국어 문체와 해석 방식을 정의합니다.

데이터 매핑, payload 필드 구조, 이미지 생성 규칙은 다른 문서에서 다룹니다. 이 문서는 사람이 블로그에 바로 올릴 수 있는 문장으로 쓰기 위한 규칙만 다룹니다.

## 1. 기본 원칙

- 존댓말로 씁니다.
- 문장은 짧게 씁니다.
- 한 문장에는 하나의 판단만 담습니다.
- 같은 판단을 여러 섹션에서 반복하지 않습니다.
- payload 문장을 그대로 복사하지 않습니다.
- 내부 개발 용어는 공개 글에 맞게 풀어서 씁니다.
- 숫자는 정확하게 쓰고, 해석은 과장하지 않습니다.
- 결과가 좋으면 좋은 이유를 저장 근거로 설명합니다.
- 결과가 나쁘면 나쁜 이유를 저장 근거로 설명합니다.
- 모르는 내용은 추측하지 않습니다.
- 없는 내용을 만들어 넣지 않습니다.
- 없는 패턴, 필터, 이미지, 비교 타임프레임은 기본적으로 쓰지 않습니다. 꼭 필요하면 한계나 보완점에만 씁니다.
- 최종 리포트는 `report-ko.html`입니다. Markdown 문체나 Markdown 이미지 문법을 최종 산출물 기준으로 쓰지 않습니다.
- Tistory hELLO 스킨에 게시할 HTML 글이라는 전제로 씁니다. 본문 컨테이너 기본 폭은 `1120px`이며, 좁은 화면에서도 제목, subtitle, bullet, 표가 읽혀야 합니다.

## 2. HTML 문체 규칙

- 첫 문단은 `<p class="lead">`에 들어갈 수 있을 만큼 선명하게 씁니다.
- 표로 보여줄 내용은 길게 풀어 쓰지 않습니다.
- 표는 목적이 분명할 때만 씁니다. 표가 커지면 비교 축을 줄이거나 목적별로 나눕니다.
- 이미지 설명은 `<figcaption>`에 들어갈 짧은 문장으로 씁니다.
- section 제목은 한국어로 씁니다.
- 영어 micro-heading을 쓰지 않습니다.
- 넓은 표는 스크롤 가능한 표로 들어간다는 전제를 두고 행을 compact하게 씁니다.
- 표는 왼쪽 정렬을 기본으로 씁니다. 숫자 컬럼은 가독성에 도움이 될 때만 오른쪽 정렬하고, 가운데 정렬을 기본값으로 두지 않습니다.
- 이미지는 본문 폭을 충분히 사용하도록 둡니다. HTML에서 이미지를 작은 고정 폭으로 강제로 줄이지 않습니다.
- 가설과 보완점은 bullet로 씁니다. HTML/CSS에서 bullet marker가 보이도록 `<ul><li>` 구조를 유지합니다.

## 3. 첫 문단

첫 문단은 전략 설명으로 시작합니다.

좋은 예:

```text
Lookback Return Momentum은 최근 N개 완료봉의 종가 수익률이 충분히 크면 그 방향의 흐름이 다음 몇 개 봉에도 이어질 수 있다고 보는 전략입니다.
```

피할 예:

```text
Binance BTCUSDT 1m / 15m 비교. 거래비용 반영 후 손익, 기대값, 비용 민감도를 중심으로 정리한 백테스트 기록입니다.
```

규칙:

- 제목과 subtitle은 전략 자체를 먼저 보여줍니다.
- main title은 전략명과 버전을 기본값으로 둡니다. `낮은 진입 기준 비교`처럼 실험 세부 내용을 title에 길게 붙이지 않습니다.
- subtitle은 version이 바뀌어도 유지되는 전략 설명을 씁니다. 예: `과거 일정 구간의 수익률을 확인하는 모멘텀 전략`.
- 실험에서 무엇을 바꿨는지는 subtitle이 아니라 `핵심 요약`이나 `해석`에서 다룹니다.
- 시장, 심볼, 타임프레임, 기간은 설정 표에서 다룹니다.
- 첫 문단에 전략명, 신호, 진입/청산 아이디어를 먼저 씁니다.
- 핵심 결과는 두 번째 문장이나 요약 표 뒤에서 연결합니다.

## 4. 금지 또는 제한 표현

아래 표현은 최종 리포트에 쓰지 않습니다.

```text
단순히
질문에서 출발한다
진단 구간
신호가 조금 맞아도
별도 변인별 이미지는 만들지 않았습니다
비용 스트레스
보수적 거래비용 가정에서 유효성이 약해진 사례
고비용 시나리오
거래비용 민감도 검증 구간
기대값이 음수로 고정되었습니다
검증 사례로 기록하는 것이 적절합니다
그것은
확실히 먹힌다
무조건 작동한다
실전 투입 가능하다
놀라운 결과
인상적인 결과
매우 유의미하다
```

아래 유형도 피합니다.

- 어색한 `기본값` 라벨.
- 영어식 setup/numbers/kicker 제목.
- 별도의 주의사항 기본 섹션.
- `해석`을 다음 보완점 제목과 합친 긴 섹션명.
- backtest라면 당연한 주문 관련 고지 문구.
- short exposure를 가짜 포지션이라고 설명하는 문구.
- 공개 리포트에서 불필요한 내부 task/run 설명.

## 5. 내부 용어 변환

### cost profile

피할 표현:

```text
high_slippage_stress
cost profile
비용 스트레스
보수적 거래비용 가정
고비용 시나리오
```

권장 표현:

```text
수수료와 슬리피지를 크게 잡고 테스트했습니다.
수수료, 스프레드, 슬리피지를 모두 반영했습니다.
거래비용을 반영한 뒤에는 순손익과 기대값이 모두 음수였습니다.
```

### persisted / locked / replay

피할 표현:

```text
persisted strategy logic
locked replay
saved replay
persisted sizing
```

권장 표현:

```text
저장된 전략 로직을 그대로 사용했습니다.
저장된 포지션 사이징 로직을 사용했습니다.
저장된 실행 결과를 기준으로 확인했습니다.
```

### pre-owner validation window

피할 표현:

```text
pre-owner validation window
pre-owner high-slippage stress 조건
owner-window 이후가 아닌 pre-owner 구간
```

권장 표현:

```text
별도 검증 구간
전략을 만든 구간이 아닌 검증 구간
재튜닝하지 않은 검증 구간
```

### hit ratio

피할 표현:

```text
hit ratio
```

권장 표현:

```text
승률
```

## 6. 비용 관련 표현

비용은 결과의 일부로 설명합니다. 비용 하나만 원인으로 단정하지 않습니다.

좋은 예:

```text
비용 차감 전 손익이 이미 충분하지 않았고, 수수료와 슬리피지를 반영한 뒤 손실 폭이 커졌습니다.
```

```text
거래 수가 많아 비용 부담이 커졌지만, 비용 차감 전 우위도 충분하지 않았습니다.
```

나쁜 예:

```text
핵심은 거래비용입니다.
```

```text
비용 때문에 탈락했습니다.
```

## 7. 결과 해석 표현

성과가 좋지 않은 경우에도 감정적으로 쓰지 않습니다.
숫자와 원인을 연결합니다.

좋은 예:

```text
수익 곡선은 전체 구간에서 하락세를 보였습니다.
```

```text
거래 수는 적지 않았지만, 승률과 기대값이 모두 낮았습니다.
```

```text
시간 청산이 많아 목표가까지 이어진 거래가 충분하지 않았습니다.
```

피할 예:

```text
성과가 지속적으로 악화되었습니다.
```

```text
전략 우위로 해석하기 어렵습니다.
```

## 8. 모멘텀 리포트 표현 규칙

시장/심볼은 테스트 개요나 제목에서 이미 보이면 전략 소개 문장에 반복하지 않습니다.

좋은 예:

```text
Lookback Return Momentum은 최근 완료봉 수익률이 기준을 넘으면 같은 방향으로 진입하는 기초 모멘텀 전략입니다.
```

피할 예:

```text
Lookback Return Momentum은 Binance BTCUSDT에서 최근 완료봉 수익률이 기준을 넘으면 같은 방향으로 진입하는 기초 모멘텀 전략입니다.
```

모멘텀 결과는 다음 항목으로 설명합니다.

- 비용 차감 전 손익.
- 비용 반영 후 순손익.
- 승률과 평균 손익.
- 손절, 익절, 시간 청산 구성.
- turnover.
- threshold와 hold window.
- 손익비와 비용 차감 후 기대값.

## 9. 전략 가정과 이론적 배경

이론적 배경은 짧지만 얕지 않게 씁니다.
전략이 왜 작동할 수 있는지와 왜 실패할 수 있는지를 함께 설명합니다.
전략 문서의 이론, 경제적 근거, 레퍼런스를 먼저 사용합니다. 리포트 작성자가 근거를 즉석에서 만들어내지 않습니다.

반드시 포함할 축:

- 전략이 이용하려는 시장 현상.
- 그 현상에서 우위가 생길 수 있는 이유.
- 경제적 또는 행동적 메커니즘.
- 성공 조건.
- 실패 조건.
- 비용, turnover, 손익비가 기대값에 미치는 영향.
- 레퍼런스 또는 근거 문헌.
- 진입 조건, 청산 조건, 비용 조건, 반대 신호 처리, 동일 캔들 처리처럼 결과 해석에 필요한 전략 규칙.

전략 규칙은 별도 기본 섹션으로 분리하지 않습니다.
이론적 배경 안에서 "이 가정이 어떤 규칙으로 구현됐는지"를 함께 보여줍니다.

레퍼런스는 긴 인용문이 아니라 짧은 연결 문장으로 씁니다.
전략 문서에 레퍼런스가 없으면 full report 작성 전에 전략 문서를 먼저 보강합니다.

좋은 예:

```text
이 전략은 최근 수익률이 단기 주문 흐름을 일부 요약한다고 봅니다.
가격 반응이 늦거나 추세 추종 참여가 이어지면 최근 움직임이 다음 몇 개 봉까지 지속될 수 있습니다.
하지만 신호가 빠를수록 거래 수가 늘고 비용 부담도 커집니다.
평균 후속 움직임이 비용과 손익비를 넘지 못하면 기대값은 낮아집니다.
```

나쁜 예:

```text
모멘텀은 가격이 오른 뒤 더 오를 수 있다는 뜻입니다.
```

## 10. 대표 거래

대표 거래는 가능한 범위에서 당시 상황을 넣습니다.

사용 가능한 근거:

- entry/exit timestamp.
- side.
- 보유 시간.
- gross PnL 대비 fee/spread/slippage 비중.
- 진입 전후 캔들 몸통과 range.
- local volume baseline 대비 거래량.
- 진입 후 추세 지속/반전/횡보 여부.
- 근처 drawdown 또는 equity curve 상태.
- 대표 거래로 고른 이유.

데이터가 없으면 추정하지 말고 생략합니다.

대표 거래 이미지를 해석할 때는 주변 시야를 전제로 합니다.

- 좋은 대표 거래 이미지는 entry 전 context, entry-to-exit 흐름, exit 후 움직임을 함께 보여줍니다.
- entry/exit candle만 좁게 잘라낸 이미지는 전략의 성공/실패 원인을 설명하기 어렵습니다.
- 이미지의 글자가 candle, marker, stop/target line과 겹치면 본문에서 억지로 해석하지 말고 이미지 생성 단계의 보완점으로 남깁니다.
- 차트 안에 긴 해석 문장을 넣지 않습니다. 차트는 구조를 보여주고, 해석 문장은 본문에서 씁니다.

## 11. 해석 섹션

최종 섹션 제목은 `해석`입니다.
별도 결론 섹션은 만들지 않습니다.

해석에서 답할 질문:

- 이번 실험은 무엇을 확인하려고 했나요?
- 저장된 결과에서는 어떤 일이 일어났나요?
- 성공했다면 어떤 조건이 성과를 만들었나요?
- 실패했다면 어떤 조건이 성과를 막았나요?
- 보완점은 무엇이고 왜 필요한가요?

성과가 좋을 때:

- 비용 차감 전 우위가 충분했는지 설명합니다.
- 비용 반영 후에도 기대값이 남은 이유를 설명합니다.
- 승률, 평균 이익, 평균 손실, 손익비, 목표가 도달 비중, drawdown을 함께 봅니다.

성과가 나쁠 때:

- gross-vs-net gap을 봅니다.
- turnover와 비용 부담을 봅니다.
- exit mix를 봅니다.
- 신호 threshold와 hold window가 충분했는지 봅니다.
- reward/risk 구조가 비용 이후에도 의미가 있었는지 봅니다.
- 테스트한 전략/버전과 더 넓은 전략군을 구분합니다.
- 저장 결과가 특정 구현, 기간, 심볼, 타임프레임, 비용 가정, 파라미터 그리드에 묶여 있으면 전략군 전체를 기각하지 않습니다.

경계 문장 예시:

```text
현재 버전은 이 조건에서 비용 반영 후 유효한 전략으로 보기 어렵습니다.
다만 이 결과만으로 전략군 전체를 기각하기는 이릅니다.
```

위 문장 뒤에는 왜 기각하기 이른지 저장 근거의 범위를 설명합니다.

- 테스트한 대상이 하나의 버전 또는 단순 구현인지 확인합니다.
- 검증 구간, 심볼, 타임프레임, 비용 가정, 파라미터 범위가 제한적이면 그 제한을 말합니다.
- 적용하지 않은 regime, 유동성, 상위 타임프레임, 방향 지속 확인, 시장 조건 필터가 있으면 일반화하지 않습니다.
- 전략군 전체로 판단 범위를 넓히려면 OOS/WFO, 랜덤 또는 기준선 비교, regime segmentation, 다른 신호 정의가 필요하다고 씁니다.

성과가 좋을 때도 같은 원칙을 적용합니다.

- 현재 결과가 좋은 버전과 조건을 설명합니다.
- 전략군 전체가 보편적으로 유효하다고 쓰지 않습니다.
- 넓은 검증이 없으면 성공을 과장하지 않습니다.

마무리:

```text
보완점은 다음과 같습니다.
```

그 뒤에는 bullet로 이유를 함께 씁니다.
`첫째`, `둘째`, `셋째`로 나열하지 않습니다.
각 보완점은 "무엇을 바꿀지"와 "왜 이번 결과가 그 보완을 요구하는지"를 함께 씁니다.
근거 없는 보완점은 쓰지 않습니다.

## 12. 버전 변경 설명

전략 버전이나 핵심 메커니즘이 바뀌면 `핵심 요약`에서 짧게 설명합니다.

좋은 예:

```text
이전 버전은 손익 기준을 고정 R로 두었고, 이번 버전은 ATR 기준으로 산정합니다.
```

규칙:

- 버전 차이는 결과 해석과 분리합니다.
- 이전/현재 차이는 한두 문장 또는 compact bullet로 충분합니다.
- 모르는 이전 버전 내용을 추정하지 않습니다.

## 13. 최종 검수 기준

리포트 작성 후 아래 기준으로 문장을 다시 봅니다.

- 사람이 블로그에 직접 쓸 문장인가?
- 최종 파일이 `report-ko.html`인가?
- hELLO 스킨 본문 폭 기준으로 제목, subtitle, 첫 섹션이 과하게 밀리지 않는가?
- HTML 컨테이너가 `1120px` 기본 폭과 모바일 여백을 지키는가?
- 표가 왼쪽 정렬로 한 덩어리처럼 읽히고, 숫자 컬럼만 필요한 경우 오른쪽 정렬되는가?
- 이미지가 본문 폭을 충분히 사용하는가?
- 첫 문단이 전략 설명으로 시작하는가?
- 제목과 subtitle이 실험 세부 문구로 과하게 길어지지 않았는가?
- version 변경이 있으면 핵심 요약에서 이전/현재 차이를 설명했는가?
- 내부 개발 용어가 그대로 노출되어 있지 않은가?
- 문장이 너무 길지 않은가?
- 같은 판단을 반복하지 않는가?
- 결과를 과장하지 않았는가?
- 실패한 버전의 결과를 전략군 전체 기각으로 확대하지 않았는가?
- 성공한 버전의 결과를 보편적 유효성으로 과장하지 않았는가?
- `그것은`을 쓰지 않았는가?
- 가설 bullet과 보완점 bullet이 눈에 보이는가?
- 표가 너무 크거나 목적이 모호하지 않은가?
- 최종 섹션이 `해석`인가?
- 별도 결론 섹션을 만들지 않았는가?
- 없는 패턴/필터/이미지/타임프레임을 불필요하게 언급하지 않았는가?
- 대표 거래 설명에 가능한 시장 상황 근거를 넣고, 없는 데이터는 만들지 않았는가?
- 비용, 승률, 기대값, drawdown, exit mix 중 핵심 원인을 직접 말했는가?
