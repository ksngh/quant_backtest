# DAILY_REPORT_STYLE.md

## 목적

이 문서는 백테스트 일일 리포트의 말투와 형식만 정의한다.

데이터 매핑 규칙, payload 필드 처리, 지표 계산 방식은 이 문서에 넣지 않는다.
이 문서는 `DAILY_REPORT_TEMPLATE.md`를 채울 때 문장이 어색해지지 않도록 하는 문체 규칙이다.

## 기본 원칙

- 존댓말로 작성한다.
- 사람이 직접 쓴 리포트처럼 짧고 명확하게 쓴다.
- 문장을 길게 늘리지 않는다.
- 한 문장에는 하나의 판단만 담는다.
- 같은 내용을 여러 섹션에서 반복하지 않는다.
- payload에 있는 표현을 그대로 복사하지 않는다.
- 내부 개발 용어는 공개 글에 맞게 풀어서 쓴다.
- 숫자는 정확하게 쓰고, 해석은 과장하지 않는다.
- 결과가 나쁘면 나쁘다고 쓴다.
- 성과가 좋을 때도 착시 가능성을 같이 본다.
- 모르는 내용은 추측하지 않는다.
- 없는 내용을 만들어 넣지 않는다.

## 문장 길이

가능하면 한 문장은 짧게 쓴다.

좋은 예:

```text
수익 곡선은 전체 구간에서 계속 내려갔습니다.
```

```text
거래 수는 적지 않았지만, 승률과 기대값이 모두 낮았습니다.
```

나쁜 예:

```text
Equity curve와 drawdown은 전체 검증 구간에서 지속적으로 악화되었으며, 이는 해당 전략이 비용 및 낮은 hit ratio를 감당하지 못했다는 점을 보여주는 검증 사례로 해석하는 것이 적절합니다.
```

수정:

```text
수익 곡선은 전체 구간에서 계속 내려갔습니다.
거래비용과 낮은 승률을 버티지 못했습니다.
```

## 말투

딱딱한 보고서 말투보다 자연스러운 분석 문장으로 쓴다.

피할 표현:

```text
확인되었습니다.
전환되었습니다.
기록하는 것이 적절합니다.
유효성이 약해졌습니다.
성과가 지속적으로 악화되었습니다.
전략 우위로 해석하기 어렵습니다.
실전 적용 가능성이 낮아진 사례입니다.
```

권장 표현:

```text
확인했습니다.
바뀌었습니다.
사례로 보는 편이 맞습니다.
성과가 약했습니다.
수익 곡선이 계속 내려갔습니다.
우위가 있다고 보기는 어렵습니다.
실전에 쓰기는 어려워 보입니다.
```

## 금지 표현

아래 표현은 사용하지 않는다.

```text
단순히
질문에서 출발한다
비용 스트레스
보수적 거래비용 가정에서 유효성이 약해진 사례
고비용 시나리오
거래비용 민감도 검증 구간
기대값이 음수로 고정되었습니다
검증 사례로 기록하는 것이 적절합니다
확실히 먹힌다
무조건 작동한다
실전 투입 가능하다
놀라운 결과
인상적인 결과
매우 유의미하다
```

## 내부 용어 변환

payload나 코드에서 쓰는 내부 용어는 그대로 쓰지 않는다.

### cost profile

피할 표현:

```text
high_slippage_stress
cost profile
비용 스트레스
보수적 거래비용 가정
고비용 시나리오
```

권장 표현:

```text
수수료와 슬리피지를 크게 잡고 테스트했습니다.
수수료, 스프레드, 슬리피지를 모두 반영했습니다.
거래비용을 반영한 뒤에는 순손익과 기대값이 모두 음수였습니다.
```

### persisted / locked / replay

피할 표현:

```text
persisted strategy logic
locked replay
saved replay
persisted sizing
```

권장 표현:

```text
저장된 전략 로직을 그대로 사용했습니다.
저장된 포지션 사이징 로직을 사용했습니다.
저장된 실행 결과를 기준으로 확인했습니다.
```

### pre-owner validation window

피할 표현:

```text
pre-owner validation window
pre-owner high-slippage stress 조건
owner-window 이후가 아닌 pre-owner 구간
```

권장 표현:

```text
별도 검증 구간
전략을 만든 구간이 아닌 검증 구간
재튜닝하지 않은 검증 구간
```

### spot-like / research-only short

피할 표현:

```text
Spot-like offline backtest; short side is research-only simulated exposure
```

권장 표현:

```text
Spot 기준의 오프라인 백테스트입니다.
Short는 실거래 주문이 아니라 연구용 가상 포지션으로 처리했습니다.
```

### hit ratio

피할 표현:

```text
hit ratio
```

권장 표현:

```text
승률
```

## 비용 관련 표현

비용 관련 문장은 자연스럽게 쓴다.

좋은 예:

```text
거래비용을 반영한 뒤에는 순손익과 기대값이 모두 음수였습니다.
```

```text
수수료와 슬리피지를 반영하자 손실 폭이 더 커졌습니다.
```

```text
비용을 빼고 봐도 성과가 약했고, 비용을 반영하면 손실 폭이 더 커졌습니다.
```

```text
이 전략은 지금 조건에서는 비용을 버티지 못했습니다.
```

나쁜 예:

```text
거래비용을 보수적으로 반영하자 순손익과 기대값이 모두 음수로 전환되었습니다.
```

```text
보수적 거래비용 가정에서 유효성이 약해진 사례입니다.
```

```text
비용 스트레스에서 탈락한 검증 사례입니다.
```

## 결과 해석 표현

성과가 좋지 않은 경우에도 감정적으로 쓰지 않는다.
숫자와 원인을 짧게 연결한다.

좋은 예:

```text
수익 곡선은 전체 구간에서 계속 내려갔습니다.
```

```text
거래 수는 252회로 적지 않았지만, 승률 3.97%와 기대값 -1,412.15는 모두 낮았습니다.
```

```text
손실은 주로 Short에서 나왔고, Long도 비용을 반영하면 기대값이 음수였습니다.
```

```text
TIME_EXIT 거래가 많았지만, 평균적으로 손실을 줄이지 못했습니다.
```

```text
현재 결과만 보면 실거래 후보로 보기는 어렵습니다.
```

피할 예:

```text
성과가 지속적으로 악화되었습니다.
```

```text
전략 우위로 해석하기 어렵습니다.
```

```text
실전 적용 가능성이 낮아진 사례로 판단됩니다.
```

## 핵심 요약 형식

핵심 요약은 숫자와 판단을 먼저 보여준다.

형식:

```text
[총 거래 수] trades. [승률]% win rate. [핵심 성과 한 줄].
```

예시:

```text
252 trades. 3.97% win rate. 거래비용을 반영한 뒤에는 순손익과 기대값이 모두 음수였습니다.
```

두 번째 문장은 전략, 시장, 기간, 핵심 결과만 담는다.

예시:

```text
T281_B1_PRIORITY_ENSEMBLE_H120_T150_S75_CF100_FF002은 Binance BTCUSDT 1분봉에서 2026-04-20부터 2026-05-19까지 테스트했을 때, 총 수익률 -35.59%와 Profit Factor 0.0584를 보였습니다.
```

그래프 뒤에는 짧은 해석만 쓴다.

좋은 예:

```text
수익 곡선은 전체 구간에서 계속 내려갔습니다.
```

```text
Drawdown은 회복 구간 없이 계속 확대되었습니다.
```

```text
결과적으로 이 전략은 지금 조건에서는 비용과 반복 손실을 버티지 못했습니다.
```

## The setup 작성 규칙

`The setup`은 짧게 쓴다.
내부 용어를 길게 붙이지 않는다.

좋은 예:

```markdown
The setup:

- 시장/심볼: Binance BTCUSDT
- 타임프레임: 1m
- 기간: 2026-04-20 00:00:00 UTC ~ 2026-05-19 23:59:00 UTC
- 진입 조건: 저장된 Task 281 priority ensemble 진입 로직을 그대로 사용했습니다.
- 청산 조건: stop, target, time exit, scout preempt exit을 적용했습니다.
- 비용 조건: 수수료, 스프레드, 슬리피지를 모두 반영했습니다.
- 포지션 사이징: 저장된 Task 281 sizing 로직을 사용했습니다.
- PR: https://github.com/ksngh/quant_backtest/pull/167
```

## The numbers 작성 규칙

숫자만 간결하게 적는다.
숫자 해석은 이 섹션에서 길게 하지 않는다.

좋은 예:

```markdown
The numbers:

- 총 거래 수: 252
- 승률: 3.97%
- 수익률: -35.5861%
- 최대 낙폭: -35.6147%
- Profit Factor: 0.0584
- Expectancy: -1,412.15
- Sharpe: -20.3805
- Sortino: -24.8541
```

## The kicker 작성 규칙

가장 중요한 해석을 한 줄로 쓴다.

좋은 예:

```text
비용을 빼고 봐도 성과가 약했고, 수수료와 슬리피지를 반영하자 손실 폭이 더 커졌습니다.
```

```text
거래 수는 충분했지만, 낮은 승률과 반복 손실이 수익 곡선을 계속 끌어내렸습니다.
```

```text
Short 손실이 전체 손실을 주도했고, Long도 비용을 반영하면 기대값이 음수였습니다.
```

나쁜 예:

```text
해당 전략은 보수적 거래비용 가정에서 유효성이 약화되었으며, 실거래 후보로 보기 어려운 비용 스트레스 탈락 사례입니다.
```

## 가설 작성 규칙

가설은 2개만 쓴다.
가설은 `~할 것이다`로 끝낸다.
너무 긴 설명형 문장을 쓰지 않는다.

좋은 예:

```markdown
- Task 281 priority ensemble은 별도 검증 구간에서도 진입 우위를 유지할 것이다.
- 슬리피지를 크게 잡으면 높은 회전율이 수익 곡선에 부담이 될 것이다.
```

나쁜 예:

```markdown
- Task 281 priority ensemble은 owner-window 이후가 아닌 pre-owner 구간에서도 동일한 진입 우위를 유지할 것이다.
- High slippage stress 조건에서는 높은 회전율 전략의 비용 민감도가 수익 곡선 하락으로 나타날 것이다.
```

## 전략 가정과 이론적 배경 작성 규칙

이론적 배경은 짧게 쓴다.
한 문장에 여러 개념을 넣지 않는다.
개념보다 결과와 연결되는 가정을 먼저 쓴다.

좋은 예:

```text
이 전략은 짧은 가격 반응과 실패한 움직임의 되돌림을 이용하려는 전략입니다.
가격이 충분히 빠르게 움직이면 목표가나 시간 청산으로 손실을 만회할 수 있다고 봤습니다.
하지만 이번 결과에서는 낮은 승률과 거래비용이 더 컸습니다.
```

나쁜 예:

```text
이 전략은 단기 가격 반응, 실패한 움직임의 되돌림, 활동성 기반 scout 진입이 비용 이후에도 남는지 확인하는 검증입니다. 가격 움직임이 충분히 빠르게 확장되면 시간 청산 또는 목표 청산으로 손실을 상쇄할 수 있다는 가정이 들어 있지만, 검증 결과에서는 비용과 낮은 hit ratio가 그 가정을 압도했습니다.
```

## 백테스트 설정 작성 규칙

설정은 사실만 쓴다.
내부 실행 모델은 짧게 풀어서 쓴다.

좋은 예:

```text
이번 백테스트는 OHLCV 데이터를 사용했습니다.
실거래 주문은 넣지 않았고, 같은 캔들에서 손절과 익절이 모두 가능한 경우는 저장된 체결 기록 기준으로 점검했습니다.
```

```text
Short는 실거래 주문이 아니라 연구용 가상 포지션으로 처리했습니다.
```

나쁜 예:

```text
OHLCV-based saved replay. Same-candle stop/target ambiguity is audited from persisted metadata; no live execution or exchange order endpoint was used.
```

## 주의해서 볼 점 작성 규칙

`주의해서 볼 점`은 3개 이하로 쓴다.
가장 중요한 착시 가능성만 남긴다.

좋은 예:

```markdown
- 수수료, 스프레드, 슬리피지를 합친 거래비용이 318,287.68로 컸습니다.
- 거래 수는 252회로 적지 않았지만, 승률 3.97%와 기대값 -1,412.15는 모두 낮았습니다.
- 손실은 주로 Short에서 나왔고, Long도 비용을 반영하면 기대값이 음수였습니다.
```

나쁜 예:

```markdown
- 총비용 318,287.68이 net PnL 악화의 핵심입니다. 비용/gross PnL 비율은 8.4712입니다.
- 완료 거래 252회로 거래 수 자체는 부족하지 않았지만, win rate +3.97%와 expectancy -1,412.15가 동시에 낮았습니다.
- SHORT 손실이 전체 손실의 대부분을 차지했고, LONG도 net 기준 기대값이 음수였습니다.
```

## 대표 거래 작성 규칙

대표 거래는 수익 거래 1개, 손실 거래 1개만 쓴다.

좋은 예:

```text
이 거래는 목표가 청산까지 이어진 좋은 사례입니다. 다만 이 거래에서도 비용이 3,158.16 발생했습니다. 큰 방향성이 없으면 비용을 이기기 어려운 구조입니다.
```

```text
이 거래는 Short 진입 이후 가격이 반대로 움직이며 손절된 사례입니다. 손실 거래 하나에서 비용이 5,183.08 발생해 최종 손실이 더 커졌습니다.
```

나쁜 예:

```text
이 거래에서는 목표 청산이 정상적으로 작동했습니다. 다만 total cost 3,158.16이 발생했기 때문에, 큰 방향성 움직임이 없으면 비용을 이기기 어려운 구조도 함께 확인됩니다.
```

## 해석 작성 규칙

해석은 3개 bullet로 끝낸다.
side metrics, exit reason metrics를 모두 나열하지 않는다.

좋은 예:

```markdown
이번 백테스트에서 확인한 내용은 다음과 같습니다.

- 수익 곡선은 전체 구간에서 계속 내려갔습니다.
- 손실은 주로 Short에서 나왔고, Long도 비용을 반영하면 기대값이 음수였습니다.
- TIME_EXIT 거래가 많았지만, 평균적으로 손실을 줄이지 못했습니다.

이번 조건에서는 T281 priority ensemble이 성과를 내지 못했습니다.
거래비용, 낮은 승률, TIME_EXIT 손실을 보면 이 전략에 우위가 있다고 보기는 어렵습니다.
```

## 결론 작성 규칙

결론은 2~3문장만 쓴다.
강한 표현보다 현재 결과 기준으로 쓴다.

좋은 예:

```text
이번 백테스트에서는 T281 priority ensemble이 거래비용을 이기지 못했습니다.
현재 결과만 보면 실거래 후보로 보기는 어렵습니다.
```

```text
이번 조건에서는 승률과 기대값이 모두 낮았습니다.
거래 수는 충분했지만, 손실 구조가 뚜렷해서 전략 우위가 있다고 보기는 어렵습니다.
```

나쁜 예:

```text
이번 백테스트에서는 T281 priority ensemble이 pre-owner high-slippage stress 조건에서 비용을 이기지 못한다는 점을 확인했습니다.
현재 결과만 기준으로 보면 이 전략은 실거래 후보가 아니라 비용 스트레스에서 탈락한 검증 사례로 기록하는 것이 적절합니다.
```

## 최종 검수 기준

리포트 작성 후 아래 기준으로 문장을 다시 본다.

- 이 문장을 사람이 블로그에 직접 쓸 것 같은가?
- 내부 개발 용어가 그대로 노출되어 있지 않은가?
- 문장이 너무 길지 않은가?
- 같은 판단을 반복하지 않는가?
- 결과를 과장하지 않았는가?
- 비용, 승률, 기대값, drawdown 중 핵심 원인을 직접 말했는가?
- `확인되었습니다`, `전환되었습니다`, `유효성`, `검증 사례` 같은 표현이 과하게 반복되지 않는가?

위 기준을 만족하지 않으면 문장을 더 짧고 직접적으로 고친다.
