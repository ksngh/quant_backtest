# Daily Report Style Rules

이 문서는 full daily report workflow에서 `report-ko.html`에 들어갈 한국어 문체와 해석 방식을 정의합니다.

데이터 매핑, payload 필드 구조, 이미지 생성 규칙은 다른 문서에서 다룹니다. 이 문서는 사람이 블로그에 바로 올릴 수 있는 문장으로 쓰기 위한 규칙만 다룹니다.

## 1. 기본 원칙

- 존댓말로 씁니다.
- 문장은 짧게 씁니다.
- 한 문장에는 하나의 판단만 담습니다.
- 같은 판단을 여러 섹션에서 반복하지 않습니다.
- payload 문장을 그대로 복사하지 않습니다.
- 내부 개발 용어는 공개 글에 맞게 풀어서 씁니다.
- 숫자는 정확하게 쓰고, 해석은 과장하지 않습니다.
- 결과가 좋으면 좋은 이유를 저장 근거로 설명합니다.
- 결과가 나쁘면 나쁜 이유를 저장 근거로 설명합니다.
- 모르는 내용은 추측하지 않습니다.
- 없는 내용을 만들어 넣지 않습니다.
- 없는 패턴, 필터, 이미지, 비교 타임프레임은 기본적으로 쓰지 않습니다. 꼭 필요하면 한계나 보완점에만 씁니다.
- 최종 리포트는 `report-ko.html`입니다. Markdown 문체나 Markdown 이미지 문법을 최종 산출물 기준으로 쓰지 않습니다.
- Tistory hELLO 스킨에 게시할 HTML 글이라는 전제로 씁니다. 본문 컨테이너 기본 폭은 `1120px`이며, 좁은 화면에서도 제목, subtitle, bullet, 표가 읽혀야 합니다.
- 형식과 데이터 표시는 V2 report처럼 충분히 보여주되, 해석 논리는 V1 report처럼 촘촘하게 씁니다.
- 모든 주요 표와 이미지는 `무엇을 보여주는가`, `왜 중요한가`, `해석을 어떻게 바꾸는가`를 본문에서 회수합니다.
- 결과는 strategy idea -> experiment/version change -> main result -> supporting driver -> limiting evidence -> bounded conclusion -> next improvement 순서로 연결합니다.
- 최종 report-facing 문장은 sentence-final `봅니다.`를 쓰지 않습니다. 직접 판단, 확인, 비교, 필요성을 말합니다.

## 2. HTML 문체 규칙

- 첫 문단은 `<p class="lead">`에 들어갈 수 있을 만큼 선명하게 씁니다.
- 표로 보여줄 내용은 길게 풀어 쓰지 않습니다.
- 표는 목적이 분명할 때만 씁니다. 표가 커지면 비교 축을 줄이거나 목적별로 나눕니다.
- 이미지 설명은 `<figcaption>`에 들어갈 짧은 문장으로 씁니다.
- section 제목은 한국어로 씁니다.
- 영어 micro-heading을 쓰지 않습니다.
- 넓은 표는 스크롤 가능한 표로 들어간다는 전제를 두고 행을 compact하게 씁니다.
- 표는 왼쪽 정렬을 기본으로 씁니다. 숫자 컬럼은 가독성에 도움이 될 때만 오른쪽 정렬하고, 가운데 정렬을 기본값으로 두지 않습니다.
- 이미지는 `.section-image` 안에서 본문 폭을 충분히 사용하도록 둡니다. HTML에서 이미지를 작은 고정 폭으로 강제로 줄이지 않습니다.
- Tistory 게시 전 owner가 이미지를 다시 삽입할 수 있으므로 `<div class="section-image">[##_Image|...|alignCenter|width="100%"|_##]</div>` 구조와 full-width CSS를 유지합니다.
- standalone `가설`, `검증 가설`, `실험 가설`, `Hypothesis` 섹션은 만들지 않습니다. 테스트한 전제는 기존 서술 섹션에 녹이고, 보완점은 bullet로 씁니다. HTML/CSS에서 bullet marker가 보이도록 `<ul><li>` 구조를 유지합니다.

## 3. 첫 문단

첫 문단은 전략 설명으로 시작합니다.

좋은 예:

```text
Lookback Return Momentum은 최근 N개 완료봉의 종가 수익률이 충분히 크면 그 방향의 흐름이 다음 몇 개 봉에도 이어질 수 있는지를 검증하는 전략입니다.
```

피할 예:

```text
Binance BTCUSDT 1m / 15m 비교. 거래비용 반영 후 손익, 기대값, 비용 민감도를 중심으로 정리한 백테스트 기록입니다.
```

규칙:

- 제목과 subtitle은 전략 자체를 먼저 보여줍니다.
- main title은 전략명과 버전을 기본값으로 둡니다. `낮은 진입 기준 비교`처럼 실험 세부 내용을 title에 길게 붙이지 않습니다.
- subtitle은 version이 바뀌어도 유지되는 전략 설명을 씁니다. 예: `과거 일정 구간의 수익률을 확인하는 모멘텀 전략`.
- 실험에서 무엇을 바꿨는지는 subtitle이 아니라 `핵심 요약`이나 `해석`에서 다룹니다.
- 시장, 심볼, 타임프레임, 기간은 설정 표에서 다룹니다.
- 첫 문단에 전략명, 신호, 진입/청산 아이디어를 먼저 씁니다.
- 핵심 결과는 두 번째 문장이나 요약 표 뒤에서 연결합니다.

## 6. 비용 관련 표현

비용은 결과의 일부로 설명합니다. 비용 하나만 원인으로 단정하지 않습니다.

좋은 예:

```text
비용 차감 전 손익이 이미 충분하지 않았고, 수수료와 슬리피지를 반영한 뒤 손실 폭이 커졌습니다.
```

```text
거래 수가 많아 비용 부담이 커졌지만, 비용 차감 전 우위도 충분하지 않았습니다.
```

나쁜 예:

```text
핵심은 거래비용입니다.
```

```text
비용 때문에 탈락했습니다.
```

## 7. 결과 해석 표현

성과가 좋지 않은 경우에도 감정적으로 쓰지 않습니다.
숫자와 원인을 연결합니다.

좋은 예:

```text
수익 곡선은 전체 구간에서 하락세를 보였습니다.
```

```text
거래 수는 적지 않았지만, 승률과 기대값이 모두 낮았습니다.
```

```text
시간 청산이 많아 목표가까지 이어진 거래가 충분하지 않았습니다.
```

피할 예:

```text
성과가 지속적으로 악화되었습니다.
```

```text
전략 우위로 해석하기 어렵습니다.
```

## 7.1 데이터 표시와 해석 회수

V2-style data display는 독자가 비교할 수 있게 충분한 표와 이미지를 제공하는 방식입니다. V1-style logic density는 그 데이터가 어떤 결론으로 이어지는지 빠짐없이 설명하는 방식입니다.

리포트는 두 기준을 함께 만족해야 합니다.

- data coverage, setup, result comparison, cost impact, exit mix, side attribution, yearly/regime attribution, representative trades가 payload에 있으면 목적을 정하고 보여줍니다.
- 표는 질문을 답해야 합니다. 예: `어느 타임프레임이 좋았는가`, `gross edge가 cost를 넘었는가`, `성과가 특정 side나 year에 몰렸는가`.
- 이미지는 시각적 근거를 답해야 합니다. 예: `equity curve가 한 구간에 몰렸는가`, `대표 거래가 전략 논리와 맞았는가`.
- `해석`에서는 주요 표와 이미지를 다시 회수합니다. 표나 이미지를 넣고도 해석에서 쓰지 않으면 제거하거나 보완합니다.
- 성과가 좋으면 success driver를 씁니다. 성과가 나쁘면 failure driver를 씁니다. 결과가 섞이면 interval, side, year, exit reason, variant별 driver를 분리합니다.
- 다음 보완점은 결과의 빈칸에서 나와야 합니다. 단순히 더 해볼 일을 나열하지 않습니다.

## 8. 모멘텀 리포트 표현 규칙

시장/심볼은 테스트 개요나 제목에서 이미 보이면 전략 소개 문장에 반복하지 않습니다.

좋은 예:

```text
Lookback Return Momentum은 최근 완료봉 수익률이 기준을 넘으면 같은 방향으로 진입하는 기초 모멘텀 전략입니다.
```

피할 예:

```text
Lookback Return Momentum은 Binance BTCUSDT에서 최근 완료봉 수익률이 기준을 넘으면 같은 방향으로 진입하는 기초 모멘텀 전략입니다.
```

모멘텀 결과는 다음 항목으로 설명합니다.

- 비용 차감 전 손익.
- 비용 반영 후 순손익.
- 승률과 평균 손익.
- 손절, 익절, 시간 청산 구성.
- turnover.
- threshold와 hold window.
- 손익비와 비용 차감 후 기대값.

## 9. 백테스트 설정 알고리즘 설명

`백테스트 설정`은 파라미터 표만으로 끝내지 않습니다.
진입, 청산, 지표, 비용 필터가 결과를 좌우하면 어떻게 작동하는지 짧게 설명합니다.

규칙:

- 먼저 사람 말로 규칙을 한 문장으로 설명합니다.
- 그 다음 필요한 경우 `의사코드` 또는 `explanatory pseudocode`로 짧은 코드 블록을 둡니다.
- 실제 source code를 그대로 옮긴 것이 아니면 정확 구현이라고 쓰지 않습니다.
- 정확 구현이라고 쓸 때는 구현 근거를 확인하고, 해당 report task가 허용할 때만 짧은 source reference를 둡니다.
- 완료봉 기준을 분명히 씁니다. 현재 의사결정 시점에서 미래 candle을 쓰지 않았다는 점이 독자에게 보여야 합니다.
- indicator는 input, window, warm-up 부족 시 처리 방식을 설명합니다.
- stop, target, time exit, 같은 캔들 처리처럼 성과 해석에 영향을 주는 청산 규칙은 설정 섹션에서 빠뜨리지 않습니다.
- 비용 필터나 reward/risk guard가 핵심이면 비용 차감 후 reward/risk가 어떻게 계산되는지 설명합니다.

좋은 예:

```text
진입 신호는 최근 L개 완료봉의 종가 수익률로 계산합니다.
현재 봉 이후 가격은 사용하지 않고, 직전 완료봉까지의 정보만 사용합니다.
```

```python
# explanatory pseudocode
lookback_return = close[t - 1] / close[t - 1 - lookback_bars] - 1

if lookback_return >= entry_threshold:
    signal = "long"
elif allow_short and lookback_return <= -entry_threshold:
    signal = "short"
else:
    signal = "flat"
```

ATR 설명 예:

```python
# explanatory pseudocode
true_range = max(
    high[t] - low[t],
    abs(high[t] - close[t - 1]),
    abs(low[t] - close[t - 1]),
)
atr = average(true_range, window=atr_period)
```

피할 예:

```text
ATR을 사용했습니다.
```

```text
최근 수익률 기준입니다.
```

## 10. 전략 가정과 이론적 배경

이론적 배경은 짧지만 얕지 않게 씁니다.
전략이 왜 작동할 수 있는지와 왜 실패할 수 있는지를 함께 설명합니다.
전략 문서의 이론, 경제적 근거, 레퍼런스를 먼저 사용합니다. 리포트 작성자가 근거를 즉석에서 만들어내지 않습니다.

반드시 포함할 축:

- 전략이 이용하려는 시장 현상.
- 그 현상에서 우위가 생길 수 있는 이유.
- 경제적 또는 행동적 메커니즘.
- 성공 조건.
- 실패 조건.
- 비용, turnover, 손익비가 기대값에 미치는 영향.
- 레퍼런스 또는 근거 문헌.
- 진입 조건, 청산 조건, 비용 조건, 반대 신호 처리, 동일 캔들 처리처럼 결과 해석에 필요한 전략 규칙.

전략 규칙은 별도 기본 섹션으로 분리하지 않습니다.
이론적 배경 안에서 "이 가정이 어떤 규칙으로 구현됐는지"를 함께 보여줍니다.

레퍼런스는 긴 인용문이 아니라 짧은 연결 문장으로 씁니다.
레퍼런스 이름만 나열하지 않습니다.
문헌이 말하는 후보 메커니즘과 현재 전략 규칙의 연결을 설명합니다.
전략 문서에 레퍼런스가 없으면 full report 작성 전에 전략 문서를 먼저 보강합니다.

필수 질문:

- 이 전략은 미래 가격 행동에 대해 어떤 가정을 하나요?
- 어떤 시장 행동 때문에 그 가정이 성립할 수 있나요?
- 어떤 위험, 비용, regime에서 그 가정이 깨질 수 있나요?
- 현재 백테스트는 그 가정 중 무엇을 테스트했고, 무엇은 테스트하지 못했나요?

좋은 예:

```text
이 전략은 최근 수익률이 단기 주문 흐름을 일부 요약한다는 전제를 둡니다.
가격 반응이 늦거나 추세 추종 참여가 이어지면 최근 움직임이 다음 몇 개 봉까지 지속될 수 있습니다.
하지만 신호가 빠를수록 거래 수가 늘고 비용 부담도 커집니다.
평균 후속 움직임이 비용과 손익비를 넘지 못하면 기대값은 낮아집니다.
```

모멘텀 설명에서 사용할 수 있는 메커니즘:

- 행동재무학적 과소반응: 새로운 정보가 가격에 즉시 모두 반영되지 않고, 지연된 매수/매도가 이어질 수 있습니다.
- 느린 포지션 조정: 큰 참여자는 유동성, 위험 한도, 벤치마크, 승인 절차, 헤지 수요 때문에 한 번에 포지션을 바꾸지 못할 수 있습니다.
- 리스크 프리미엄과 tail risk: 모멘텀 수익은 급격한 반전이나 crash 위험을 부담한 보상일 수 있습니다.
- 헤저와 투기자 구조: 선물 또는 파생상품 시장에서는 투기자가 헤저의 위험 이전 수요를 받아주는 대가로 수익을 얻는 구조를 검토할 수 있습니다.
- Bitcoin spot caveat: 주식/선물 문헌을 spot Bitcoin에 그대로 적용하지 말고, 시장 구조 차이와 현재 테스트 범위를 함께 씁니다.

수학식은 선택 사항입니다. 쓰는 경우 한두 줄로 끝내고 바로 한국어로 풉니다.

```text
r_t^{(L)} = P_t / P_{t-L} - 1
signal_t = sign(r_t^{(L)})
```

위 식은 최근 L개 완료봉 수익률의 방향을 신호로 쓴다는 뜻입니다.

나쁜 예:

```text
모멘텀은 가격이 오른 뒤 더 오를 수 있다는 뜻입니다.
```

```text
Jegadeesh and Titman(1993)와 Moskowitz, Ooi, and Pedersen(2012)가 모멘텀의 배경입니다.
```

## 11. 대표 거래

대표 거래는 가능한 범위에서 당시 상황을 넣습니다.

사용 가능한 근거:

- entry/exit timestamp.
- side.
- 보유 시간.
- gross PnL 대비 fee/spread/slippage 비중.
- 진입 전후 캔들 몸통과 range.
- local volume baseline 대비 거래량.
- 진입 후 추세 지속/반전/횡보 여부.
- 근처 drawdown 또는 equity curve 상태.
- 대표 거래로 고른 이유.

데이터가 없으면 추정하지 말고 생략합니다.

대표 거래는 trade story와 diagnostic interpretation을 함께 씁니다.
아래 질문은 작성자가 확인해야 하는 항목이지, 최종 리포트의 heading이나 체크리스트가 아닙니다.

- 왜 그 거래가 발생했는가.
- 진입 조건이 저장된 규칙대로 작동했는가.
- 청산 조건이 의도대로 작동했는가.
- 수익/손실이 전략 논리에서 나온 것인가, 우연한 변동성에서 나온 것인가.
- 이 거래가 전체 성과를 왜곡하고 있는가.
- 같은 유형의 거래가 반복적으로 나타나는가.
- 백테스트 엔진이나 체결 로직 버그 가능성 신호가 있는가.

규칙:

- 위 질문을 `진입 조건`, `청산 조건`, `버그 가능성` 같은 visible heading으로 만들지 않습니다.
- `진입 조건은 정상 작동했습니다`처럼 얕게 쓰지 않습니다. 어떤 저장 근거가 그 판단을 뒷받침하는지 함께 씁니다.
- 단일 trade chart로 볼 수 있는 사실과 전체 거래군 통계가 필요한 판단을 구분합니다.
- 반복 유형이나 성과 왜곡 여부를 판단할 aggregate evidence가 없으면 한계나 보완점으로 씁니다.
- 엔진/체결 로직 bug 가능성은 timestamp 역전, 비정상 fill price, 같은 캔들 stop/target 충돌 처리 누락, 비용 누락 같은 구체 신호가 있을 때만 언급합니다.

대표 거래 이미지를 해석할 때는 주변 시야를 전제로 합니다.

- 좋은 대표 거래 이미지는 entry 전 context, entry-to-exit 흐름, exit 후 움직임을 함께 보여줍니다.
- entry/exit candle만 좁게 잘라낸 이미지는 전략의 성공/실패 원인을 설명하기 어렵습니다.
- 이미지의 글자가 candle, marker, stop/target line과 겹치면 본문에서 억지로 해석하지 말고 이미지 생성 단계의 보완점으로 남깁니다.
- 차트 안에 긴 해석 문장을 넣지 않습니다. 차트는 구조를 보여주고, 해석 문장은 본문에서 씁니다.

## 12. 해석 섹션

최종 섹션 제목은 `해석`입니다.
별도 결론 섹션은 만들지 않습니다.

해석에서 답할 질문:

- 이번 실험은 무엇을 확인하려고 했나요?
- 저장된 결과에서는 어떤 일이 일어났나요?
- 성공했다면 어떤 조건이 성과를 만들었나요?
- 실패했다면 어떤 조건이 성과를 막았나요?
- 보완점은 무엇이고 왜 필요한가요?

성과가 좋을 때:

- 비용 차감 전 우위가 충분했는지 설명합니다.
- 비용 반영 후에도 기대값이 남은 이유를 설명합니다.
- 승률, 평균 이익, 평균 손실, 손익비, 목표가 도달 비중, drawdown을 함께 확인합니다.
- 어느 interval, side, year, exit reason, variant가 성과를 만들었는지 attribution으로 분리합니다.
- 현재 조건에서의 성공과 넓은 일반화의 한계를 함께 씁니다.

성과가 나쁠 때:

- gross-vs-net gap을 확인합니다.
- turnover와 비용 부담을 확인합니다.
- exit mix를 확인합니다.
- 신호 threshold와 hold window가 충분했는지 확인합니다.
- reward/risk 구조가 비용 이후에도 의미가 있었는지 확인합니다.
- 테스트한 전략/버전과 더 넓은 전략군을 구분합니다.
- 저장 결과가 특정 구현, 기간, 심볼, 타임프레임, 비용 가정, 파라미터 그리드에 묶여 있으면 전략군 전체를 기각하지 않습니다.

성과가 섞여 있을 때:

- 평균 결과 하나로 덮지 않습니다.
- interval, side, year, exit reason, variant별로 무엇이 결과를 밀었는지 분리합니다.
- result comparison, exit mix, side attribution, yearly/regime attribution을 함께 회수합니다.
- 특정 구간이나 방향이 결과를 만든 경우 regime-specific 또는 side-specific으로 한정합니다.

경계 문장 예시:

```text
현재 버전은 이 조건에서 비용 반영 후 유효한 전략으로 보기 어렵습니다.
다만 이 결과만으로 전략군 전체를 기각하기는 이릅니다.
```

위 문장 뒤에는 왜 기각하기 이른지 저장 근거의 범위를 설명합니다.

- 테스트한 대상이 하나의 버전 또는 단순 구현인지 확인합니다.
- 검증 구간, 심볼, 타임프레임, 비용 가정, 파라미터 범위가 제한적이면 그 제한을 말합니다.
- 적용하지 않은 regime, 유동성, 상위 타임프레임, 방향 지속 확인, 시장 조건 필터가 있으면 일반화하지 않습니다.
- 전략군 전체로 판단 범위를 넓히려면 OOS/WFO, 랜덤 또는 기준선 비교, regime segmentation, 다른 신호 정의가 필요하다고 씁니다.

성과가 좋을 때도 같은 원칙을 적용합니다.

- 현재 결과가 좋은 버전과 조건을 설명합니다.
- 전략군 전체가 보편적으로 유효하다고 쓰지 않습니다.
- 넓은 검증이 없으면 성공을 과장하지 않습니다.

마무리:

```text
보완점은 다음과 같습니다.
```

그 뒤에는 bullet로 이유를 함께 씁니다.
`첫째`, `둘째`, `셋째`로 나열하지 않습니다.
각 보완점은 "무엇을 바꿀지"와 "왜 이번 결과가 그 보완을 요구하는지"를 함께 씁니다.
근거 없는 보완점은 쓰지 않습니다.

## 13. 버전 변경 설명

전략 버전이나 핵심 메커니즘이 바뀌면 `핵심 요약`에서 짧게 설명합니다.

좋은 예:

```text
이전 버전은 손익 기준을 고정 R로 두었고, 이번 버전은 ATR 기준으로 산정합니다.
```

규칙:

- 버전 차이는 결과 해석과 분리합니다.
- 이전/현재 차이는 한두 문장 또는 compact bullet로 충분합니다.
- 모르는 이전 버전 내용을 추정하지 않습니다.

## 14. 최종 검수 기준

리포트 작성 후 아래 기준으로 문장을 다시 점검합니다.

- 사람이 블로그에 직접 쓸 문장인가?
- 최종 파일이 `report-ko.html`인가?
- hELLO 스킨 본문 폭 기준으로 제목, subtitle, 첫 섹션이 과하게 밀리지 않는가?
- HTML 컨테이너가 `1120px` 기본 폭과 모바일 여백을 지키는가?
- 표가 왼쪽 정렬로 한 덩어리처럼 읽히고, 숫자 컬럼만 필요한 경우 오른쪽 정렬되는가?
- 이미지가 `.section-image` 안에서 본문 폭을 충분히 사용하는가?
- 첫 문단이 전략 설명으로 시작하는가?
- 제목과 subtitle이 실험 세부 문구로 과하게 길어지지 않았는가?
- version 변경이 있으면 핵심 요약에서 이전/현재 차이를 설명했는가?
- 내부 개발 용어가 그대로 노출되어 있지 않은가?
- 문장이 너무 길지 않은가?
- 같은 판단을 반복하지 않는가?
- 결과를 과장하지 않았는가?
- 실패한 버전의 결과를 전략군 전체 기각으로 확대하지 않았는가?
- 성공한 버전의 결과를 보편적 유효성으로 과장하지 않았는가?
- `그것은`을 쓰지 않았는가?
- standalone `가설`/hypothesis 섹션을 만들지 않았고, 보완점 bullet이 눈에 보이는가?
- 표가 너무 크거나 목적이 모호하지 않은가?
- 최종 섹션이 `해석`인가?
- 별도 결론 섹션을 만들지 않았는가?
- 없는 패턴/필터/이미지/타임프레임을 불필요하게 언급하지 않았는가?
- 대표 거래 설명에 가능한 시장 상황 근거를 넣고, 없는 데이터는 만들지 않았는가?
- 대표 거래 diagnostic 질문을 별도 목차나 체크리스트로 만들지 않고 자연스럽게 녹였는가?
- `백테스트 설정`에서 핵심 rule/indicator가 파라미터 표만으로 끝나지 않고 작동 방식이나 의사코드로 설명됐는가?
- 이론적 배경이 레퍼런스 이름 나열이 아니라 메커니즘, 실패 조건, 현재 백테스트의 증거 경계를 설명하는가?
- 비용, 승률, 기대값, drawdown, exit mix 중 핵심 원인을 직접 말했는가?
- 주요 표와 이미지가 `해석`에서 다시 회수됐는가?
- 표와 이미지마다 무엇을 보여주는지, 왜 중요한지, 해석을 어떻게 바꾸는지 설명했는가?
- 성공/실패/혼합 결과의 driver가 저장된 수치와 attribution으로 설명됐는가?
- 최종 report-facing 문장에 sentence-final `봅니다.`가 남아 있지 않은가?
