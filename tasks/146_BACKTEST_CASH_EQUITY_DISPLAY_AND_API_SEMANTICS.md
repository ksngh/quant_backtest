# Goal

Make backend/API/frontend display semantics align with the new cash, equity, free-cash, and margin metadata so users do not interpret `cash_after` as spendable cash when shorts are open.

This task is limited to user-visible/read-model semantics after engine and CLI behavior are complete.

# Context

Even after the engine exposes account-state fields, the dashboard/API can remain misleading if it shows `cash_after` as if it were free cash. This task updates presentation semantics and API contract text after the underlying fields exist.

This task should be skipped or reduced if the project has no backend/frontend path currently rendering these fields.

# Scope

- Audit backend/API/frontend display of:
  - `cash_after`
  - `ending_cash`
  - `equity_after`
  - `final_equity`
  - free-cash/margin/locked-proceeds fields from Task 144.
- Update API serialization to include additive fields if needed.
- Update frontend types to match API output if frontend consumes the fields.
- Update UI labels/tooltips/warnings so `cash_after` is not presented as free buying power under short exposure.
- Add fallback behavior for legacy runs missing new metadata.
- Add backend/frontend tests where applicable.

# Out of Scope

- Changing engine accounting behavior.
- Adding new sizing/margin policy.
- Refactoring backend/frontend architecture.
- Large visual redesign.
- Live trading controls.
- Exchange API calls.

# Requirements

- API output must remain backward-compatible for legacy runs.
- New account-state metadata must be surfaced or preserved where users inspect executions/trades.
- Frontend labels must distinguish cash balance, equity, and free cash/buying power when available.
- Legacy runs missing metadata must render with safe fallback text, not misleading certainty.
- Short-model limitations must remain visible where relevant.
- No API or UI path may imply that simulated margin is real exchange margin.
