# Task 060: Full Backtest Result Persistence

# Goal

Define an implementation task so every backtest run result is saved in persistent storage for later analysis, without expanding scope into live trading or dashboard features.

# Source Requirement

"백테스트 결과를 다 저장할 수 있도록 만들어줘"

(Owner intent: Ensure backtest results are not transient and can be retained comprehensively.)

# Extracted Roles

- Owner role:
  - Approve what "all backtest results" must include as required fields.
  - Approve retention expectations (append-only history vs overwrite behavior).
- Supporting roles:
  - Backtest runner/CLI layer passes complete run output to persistence use case.
  - Persistence module saves each run and associated trade/event rows with stable identifiers.
  - Read-model/query layer remains compatible with historical retrieval.
  - Tests verify that every executed backtest run is persisted.
- Forbidden roles:
  - No live trading or real exchange order execution.
  - No risk-management redesign.
  - No dashboard, scheduler, or infrastructure expansion beyond current persistence architecture.

# Context

The project already includes PostgreSQL-based backtest persistence foundations and graph-ready read models. The requested task is to close any remaining gaps so backtest outcomes are fully retained per run and retrievable for future review.

# Scope

- Identify supported backtest entrypoints currently returning in-memory/console summaries.
- Ensure each supported backtest execution path persists one run record plus related detail rows (trades/signals/events as defined by current contracts).
- Preserve deterministic linkage between run metadata and detail records.
- Define expected behavior for repeated runs (no accidental destructive overwrite unless explicitly configured).
- Add/update tests validating full persistence behavior across representative backtest flows.
- Update docs only where behavior/usage changes are user-visible.

# Out of Scope

- Live trading, real order execution, leverage/futures behavior.
- New dashboard/reporting UI.
- Data science/ML post-processing pipelines.
- External warehousing or analytics platform integration.
- Broad schema redesign unrelated to full result retention.

# Requirements

- For each completed backtest run, persistence logic must store a durable run-level record.
- Associated detailed outcomes generated by the backtest (e.g., closed trades and summary metrics; and any existing supported signal/event details) must be saved for the same run id.
- Persistence failures must be surfaced explicitly (no silent drop of result rows).
- Existing CLI/API user-facing contracts should remain backward compatible unless task-approved changes are documented.
- No secrets or API keys may be hardcoded or logged intentionally.
- Keep implementation incremental and limited to task-related modules/tests.
